Task API

from celery_cloud import task, Retry, Ignore, Reject (see Server: the Celery-like task API).

Celery-like API for local tasks (task://module/function).

The original contract keeps working: a plain function f(args, kwargs) receives the list of positional arguments and the dict of keyword arguments. Decorating a function with task() switches it to the natural calling convention and adds what Celery’s @app.task offers: bind, self.request, self.retry(), self.update_state(), autoretry_for, backoff and time limits:

from celery_cloud import task

@task(bind=True, max_retries=3, default_retry_delay=30)
def fetch(self, url: str) -> str:
    try:
        return download(url)
    except ConnectionError as exc:
        raise self.retry(exc=exc)

Ask the runner to run this task again later (use as raise self.retry()).

Parameters:

  • exc – The exception that caused the retry; it is the failure reported when the retries run out.

  • countdown – Seconds to wait (default: default_retry_delay).

  • eta – Absolute time of the next attempt; wins over countdown.

  • max_retries – Overrides the max_retries of the task.

Raises:

Retry – Always, unless the retries are exhausted, in which case exc is raised (or MaxRetriesExceededError when there is none).

Runtime

The services a running task can reach (custom states, revocation), published by the runner for the duration of the task.

What task code can reach while the runner executes it.

The runner publishes a Runtime for the duration of a task, and TaskContext (self of a bound task) talks to it. Keeping this in a context variable lets task code stay independent from the backend and from AWS.
