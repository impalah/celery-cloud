Exceptions

All the exceptions of the runner derive from RunnerBaseException. The handler never lets them escape: it converts them into a FAILURE state in the backend, a failed task in the response, or an entry in batchItemFailures (see Concepts and behaviour).

Exceptions for task code

Raised or used inside tasks (from celery_cloud import ...). The client receives the Celery classes of the same name.

Exceptions raised inside task code by the runner itself.

They are plain Exception subclasses (not RunnerBaseException) because user code can catch them, exactly as with Celery’s own classes of the same name. celery_module tells the runner which module to report in a FAILURE result: the Celery client rebuilds the exception from exc_module + exc_type, so reporting celery.exceptions makes except celery.exceptions.SoftTimeLimitExceeded work on the client.
